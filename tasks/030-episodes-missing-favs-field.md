## Задача

Пользователь сообщил: «в сериалах все так же невозможно загрузить список
серий» (баг #2, проявляется и на свежей сборке после #027/#028). UI показывает
`ERROR_EPISODES = "Не удалось загрузить список серий. Попробуйте ещё раз."`
(`ui/src/details-store.ts`), что означает провал на уровне
`api.episodes()` → `kino-ipc` → `kino-api::episodes_list()`/`parse_episodes_html()`.

## Расследование (сделано lead-агентом, используй как есть)

`crates/kino-api/src/api.rs::episodes_list()` (строки ~87-132) шлёт POST на
`/ajax/get_cdn_series/` с формой **только** `{id, translator_id,
action:"get_episodes"}`.

Сверка с независимой эталонной реализацией `kristal374/hdrezka-api` (Python,
MIT, упомянута в `ARCHITECTURE.md`) — `HDrezka/player/base_movie.py::_get()`:
для действия `get_episodes` реально отправляемые поля —
`{id, translator_id, favs, action}` (плюс query-параметр `t=<unix_ms>`,
cache-buster). **Поле `favs` в нашей реализации отсутствует вообще.**

`favs` — значение скрытого инпута `<input id="ctrl_favs">` на странице фильма
(см. `movie_player_builder.py::extract_favs()` в эталонной либе — UUID-подобная
строка). Грепом по всему `kino-api` подтверждено: `ctrl_favs` фигурирует
только в `crates/kino-api/src/sanitize.rs` (строки ~15, 262) как цель
PII-редакции тестовых фикстур — т.е. значение знают только тесты-санитайзеры,
никто не достаёт его из реальной страницы и не шлёт в запрос.

**Гипотеза (не 100% подтверждена без живого ответа сервера, но это
единственный конкретный протокольный пробел, который удалось найти)**:
HDrezka либо отклоняет/иначе отвечает на `get_episodes` без `favs`, либо
теряет часть данных. Это объясняет постоянный провал независимо от конкретного
сериала.

   `<input id="ctrl_favs" value="...">` → строка `favs`. Если инпута нет на
   странице — не паниковать и не ошибаться, использовать пустую строку
   (эталонная либа тоже не гарантирует её наличие на 100% страниц).
2. Решить, где хранить `favs`: либо на `MediaDetails` (новое публичное поле —
   тогда это смена публичного API `kino-core`/`kino-api`, обнови `CRATE.md`
   обоих крейтов и ВСЕ места создания `MediaDetails` в тестах/фикстурах),
   либо извлекать по требованию прямо из уже сохранённого `details.raw_html`
   в момент вызова `episodes_list()`/`stream_url()` (дешевле по объёму правок,

3. `crates/kino-api/src/api.rs::episodes_list()` — добавить `favs` в форму

4. Проверить `stream_url()`/функцию для `action=get_stream` в том же файле
   (строки после ~135, не до конца разобраны лид-агентом) — по эталонной либе
   `favs` отправляется для ЛЮБОГО action, не только `get_episodes`. Если там

   два места).
5. Обновить тестовые фикстуры в `crates/kino-api/tests`/`src/sanitize.rs` при
   необходимости — не ломать существующие тесты, добавить при необходимости
   новый тест на извлечение `favs` из HTML с `ctrl_favs`.
6. **Если у тебя будет возможность** свериться с другой эталонной либой
   (`ndenissov/HDRezka`, JS/TS, тоже упомянута в `ARCHITECTURE.md`) на GitHub —
   сверь, совпадает ли её поведение с `kristal374/hdrezka-api`. Не обязательно,
   но повышает уверенность в фиксе.

## Ограничения

**ВАЖНО — копия ограничений окружения заказчика из AGENTS.md, обязательна:**
Машина заказчика — слабый Intel Mac (i3-1000G4, 2 ядра, 8 ГБ ОЗУ, macOS
13.7.8). `kino-api` — чистый HTTP/парсинг крейт, НЕ линкует `-lmpv`, поэтому
`cargo check -p kino-api`/`cargo test -p kino-api` **локально разрешены и
предпочтительны** для быстрой итерации (в отличие от `kino-player`/`src-tauri`).

и сборка — только через CI, не локально. Не запускай `cargo tauri dev`/
`.app`/`cargo run -p kinobox-app`.

- Не выдумывай формат HDrezka API — это протокольное изменение, при малейшей
  неуверенности сверяйся с кодом эталонных библиотек (уже процитирован путь
  выше), не с памятью/догадками.
- Если меняется публичный API `kino-api`/`kino-core` (например, новое поле
  `MediaDetails::favs`) — обнови `CRATE.md` обоих крейтов в том же коммите.
- Не логировать `favs`/куки/токены в открытом виде за пределами уже
  существующей санитайзинг-инфраструктуры (`sanitize.rs`).

## Выполнение (subagent deepseek-v4-pro, 17.11.2026)

Сделан фикс. Выбран «дешёвый» вариант из ТЗ: `favs` не добавлялся в публичный
`MediaDetails`, а извлекается по требованию из `MediaDetails::raw_html` (уже
есть на структуре, `#[serde(skip)]`) в момент вызова — публичный API `kino-core`
НЕ менялся; изменились только inherent-сигнатуры `HdrezkaApi::episodes_list`
и `stream_url` (добавлен `favs: &str`).

Что сделано:

- `parse::extract_favs(html) -> Option<String>` — чистый парсер
  `input#ctrl_favs` → `value`; `None`, если инпута нет (пустая строка в форме).
- `episodes_list` и `stream_url` принимают `favs` и добавляют поле в форму
  POST `/ajax/get_cdn_series/` (для ЛЮБОГО action, как в эталонных либах —
  сверено с `kristal374/hdrezka-api` `construct_types.py`/`base_movie.py`).
- `provider_impl::episodes`/`streams` достают `favs` из `raw_html` и пробрасывают.
- Тесты: `extract_favs` (есть/нет/пустой инпут); моки форм в `api.rs` обновлены;
  интеграционный тест `kino-ipc::streams_for_series_episode_delegates_to_provider`
  обновлён (фикстура `series_details_html` получила `input#ctrl_favs`, матчер
  тела — поле `favs`).
- `CRATE.md` (kino-api): обновлены сигнатуры и описание AJAX-формы. `kino-core`
  не менялся.

Нюансы:

- `favs` в лог пишется только как `(есть)`/`(пусто)` через `redact_favs` —
  сам UUID-подобный токен не логируется.
- Фикс **эмпирически не подтверждён** без живого запроса к HDrezka (внешний
  сервис, CI его не дёргает). Живая проверка списка серий — только у заказчика
  после сборки.
- CI зелёный: `cargo test --workspace` (включая `kino-api` + `kino-ipc`),
  clippy, fmt, cross-check, bindings, ui — все 3 job'а `pass`.
