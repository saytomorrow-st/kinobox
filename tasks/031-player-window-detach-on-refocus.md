## Задача

Пользователь сообщил (после сборки, включающей фикс #027 центрирования/фокуса
плеера): «я когда запускаю плеер он правильно появляется, но когда я
фокусирую окно самого приложения, плеер отделяется и больше с ним нельзя
взаимодействовать пока не убью приложение». Это НЕ тот же баг, что #027
чинил (там было неверное появление/нефокус при ОТКРЫТИИ) — это НОВОЕ
проявление: взаимодействие ломается именно при переключении фокуса ОБРАТНО на
`main`, уже ПОСЛЕ того, как `player` корректно появился.

## Расследование (сделано lead-агентом, используй как есть)

`src-tauri/tauri.conf.json` — у окна `player` **нет поля `parent`** (это
окно-сиблинг `main`, не дочернее). `player-controls` имеет `parent: "player"`
— то есть следует только за `player`, но сам `player` ни с чем не связан.

`src-tauri/src/windows.rs::open_player()` (строки ~80-121): единственный
зарегистрированный `window.on_window_event` на `player` — обработчик
`CloseRequested`/`Destroyed`. **Нет обработчика `Focused`/`Unfocused`** —
никакой код не реагирует на то, что происходит с `player`, когда `main`
получает фокус обратно. После `show()` вызывается `set_focus()` на `player`,
затем безусловно вызывается `open_player_controls()`, который ТОЖЕ вызывает
`show()`+`set_focus()` на `player-controls` — то есть реально последним
получает фокус `player-controls`, а не `player` сам (эта деталь не связана с
текущим багом напрямую, но может усугублять).

Гипотезы корня (НЕ подтверждены экспериментально — живой GUI-запуск
агенту запрещён, нужна проверка через CI/логическое рассуждение + мнение
заказчика после сборки):

1. **Отсутствие родительской связи `player` → `main`.** На macOS/AppKit
   сиблинг-окно без `parent` не имеет автоматического порядка
   (`addChildWindow`) относительно другого окна приложения — когда `main`
   становится key window, `player` (особенно с `decorations: false`,
   безрамочное) может уйти за `main` по z-order и/или потерять способность
   принимать события (борderless-окна на macOS по умолчанию часто не могут
   стать key window повторно без явного `canBecomeKeyWindow`/`makeKeyWindow`
   пере-ассерта).
2. Решение части #2: `player-controls` живёт как `parent:"player"` — если
   `player` теряет key-статус/уходит за `main`, `player-controls` как child
   может последовать за ним (тоже перестать быть интерактивным), что
   согласуется с «плеер отделяется и больше с ним нельзя взаимодействовать».

## Нужно сделать

Варианты (выбери и реализуй наиболее надёжный, подтверди логикой кода/
документацией Tauri 2.x, если нашёл — иначе явно опиши в «Заметках», что
выбрано эмпирически и требует проверки заказчиком):

1. **Предпочтительно**: дать `player` реальную родственную связь с `main` —
   проверь, поддерживает ли `tauri::window::WindowBuilder` (не
   `WebviewWindowBuilder`!) метод `.parent()`/эквивалент в Tauri 2.x (версия
   закреплена в `Cargo.lock`, сверься с точной версией перед выводами) —
   `player` создаётся через `WindowBuilder::from_config`, не через
   `WebviewWindowBuilder`, так что API может отличаться. Если поддерживает —
   указать `main` как родителя при создании `player` (либо через
   `tauri.conf.json`, либо программно в `open_player()`).
2. Добавить `on_window_event` на `main` (или на `player`) для `Focused`,
   который при получении фокуса `main`, если `player` всё ещё открыт,
   явно переупорядочивает/переассертит окна — например вызывает
   `player_window.set_focus()` снова ИЛИ явно поднимает его уровень/порядок
   так, чтобы оно оставалось кликабельным, но не обязательно поверх `main`
   (нужно сохранить ожидаемое поведение — пользователь хочет переключаться
   МЕЖДУ окнами, не чтобы `player` вечно оставался topmost; нужно именно
   чтобы `player` оставался ИНТЕРАКТИВНЫМ при повторном фокусе на него, а не
   залипал «мёртвым»).
3. Проверить, не связана ли проблема с `decorations: false` на `player` —
   если это окно без рамки не может штатно становиться key window на
   повторном фокусе, возможно, нужен явный native override (через
   `raw-window-handle`/`objc2-app-kit`, аналогично тому, что уже сделано в
   `crates/kino-player/src/render/macos.rs` для доступа к `NSView` — похожий
   паттерн, если потребуется вызвать `[NSWindow setCanBecomeKeyWindow:]` или
   аналог через нативный API).

## Заметки

**Реализовано (deepseek-v4-pro, 17.11.2026).** Выбран вариант 2 (переассерт фокуса на
`Focused`), вариант 1 (родительская связь `player` → `main`) отклонён осознанно.

Почему не вариант 1: сверено с исходниками `tauri-2.12.5`/`tao-0.37.2` (версии из
`Cargo.lock`). `WindowBuilder::parent()` на macOS вызывает `addChildWindow:ordered:Above`
(`tao/src/platform_impl/macos/window.rs:301`). Это привязывает `player` к `main` — окно
начинает перемещаться/сворачиваться вместе с родителем, а пользователю нужны два
**независимых** окна, между которыми он переключается. Плюс `addChildWindow` не решает
«мёртвое на повторном фокусе», он решает порядок.

Почему не вариант 3: `canBecomeKeyWindow` у `TaoWindow` возвращает `focusable`
(`tao/src/platform_impl/macos/window.rs:408`), а `focusable` по умолчанию `true`
(`tao/src/window.rs:316`) и не зависит от `decorations: false`. Значит окно по-прежнему
может становиться key-окном; нативный override не требуется.

Что сделано: в `src-tauri/src/windows.rs::open_player()` расширен существующий
`on_window_event` на `player` — на `WindowEvent::Focused(true)` явно вызывается
`set_focus()` на `player-controls` (дочерний оверлей, реальная интерактивная поверхность),
чтобы при возврате фокуса на плеер оверлей снова поднялся вперёд и стал кликабельным.
`main` не трогается — переключение между окнами сохраняется. Правки #027 (`set_focus()`
после `show()`, `center: true`) не откатывались, логика добавлена поверх. Обновлён
`src-tauri/CRATE.md` (продолжение раздела про #027). Публичный API `kino-player` не менялся.

**ТРЕБУЕТ ЖИВОЙ ПРОВЕРКИ ПОЛЬЗОВАТЕЛЕМ.** Баг не подтверждён живым GUI-тестом — запуск
приложения агенту запрещён, это лучшая гипотеза на основе чтения кода. Сценарий для
проверки после установки сборки: «открыть плеер → кликнуть на главное окно → попробовать
снова кликнуть по плееру (кнопки/seek/громкость)». Явно попрошено в описании PR.
